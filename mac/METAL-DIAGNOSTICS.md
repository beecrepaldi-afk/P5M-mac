# Metal presentation diagnostics on macOS 27

macOS 27's `metalperftrace` collects Metal performance history already recorded by the OS. These commands do not launch P5M, connect to a console, change recording settings, or capture audio/video.

Raw `.atrc` traces can include other apps, process IDs, paths, layer configuration and timestamps. Keep them local. Share only the numeric report generated by this tool. The analyzer exports a fixed whitelist of numeric metrics, without process names, process/layer IDs, paths, display/console identifiers or arbitrary state metadata.

## Collect after playing

Run from the repository root, after a session you started yourself:

```sh
python3 mac/metal_diagnostics.py collect --last 5m --directory /private/tmp/p5m-metal-traces
```

Choose the `.atrc` file created in that directory. Use a visible, steady gameplay interval, excluding startup, menus, occlusion, minimization, mode transitions and quitting. Dates must have an explicit timezone. For example:

```sh
python3 mac/metal_diagnostics.py analyze \
  --trace /private/tmp/p5m-metal-traces/MetalPerfTrace_EXAMPLE.atrc \
  --start 2026-10-07T02:28:50-03:00 \
  --end 2026-10-07T02:29:25-03:00 \
  --output /private/tmp/p5m-metal-report.json
```

For an existing local overview JSON, substitute `--timeline FILE.json` for `--trace`. It must have been generated with `metalperftrace overview --json --json-include-timeline`. Analysis of JSON works without macOS 27; collection/trace decoding requires its installed tool. If a command fails, run `metalperftrace collect --help` or `metalperftrace overview --help` locally; this wrapper deliberately avoids exporting raw diagnostic errors containing personal paths.

## Read the report

Each `groups` entry is one P5M/chiaki process layer with samples inside the requested interval. Groups remain separate; summing their FPS would create fictitious throughput. No automatic selection of gameplay is made. Very small windows may contain no complete samples.

`presented_fps` is presented frames divided by actual sampled duration; `skipped_fps` is the system's skipped-frame count over that duration. OS presentation counts can include UI redraws and are not guaranteed to mean unique decoded video frames. Compare with P5M's `[presentation]` and `[pacing]` diary lines.

`gpu_ms` measures GPU work; `drawable_wait_ms` measures drawable acquisition waits. `on_glass_interval_ms` describes intervals reported by the OS for presentation. `render_to_completion_ms` covers the system's rendering pipeline, not the full PS5-to-display latency. `gpu_done_to_completion_ms` includes downstream completion/reporting delay; it is not proof of compositor delay alone. Means are weighted by metric sample count. The numeric `timeline` preserves each OS sample with its offset relative to the requested start, duration and frame counts/FPS; it exports no wall-clock timestamps. A missing measurement is `null`, never an invented zero.

Only timeline samples wholly contained in the interval are counted. `excluded_boundary_samples` records samples cut by either endpoint; no fractional frame counts are estimated. Never use an entire trace average when part of it includes a hidden or idle app.

## StateReporting contexts

The macOS 27 SDK exposes `SRStateReporter`. Use a stable domain such as `io.github.beecrepaldi-afk.p5m.mac.presentation`, fixed labels such as `Streaming`, `Menu`, and `Hidden`, and fixed, nonpersonal metadata: HDR enabled, VSync enabled, display-link path, fullscreen mode and pixel format. The state should describe actual applied rendering configuration.

Report only state changes on a serialized path. The SDK rate-limits updates more frequent than user interaction timescales; frame counters and deadlines should remain in P5M's numeric diary rather than per-frame state reports. The SDK accepts only `NSNumber`, `NSString` and `NSDate` metadata values. Clear the active state with a nil label at teardown. Guard runtime availability and weak-link the framework if supporting older systems.

State contexts help group traces, but do not establish visibility or direct-to-display eligibility by themselves. Confirm the selected test interval and compare identical HDR/fullscreen settings when evaluating pacing.

Primary references: [Apple's Metal performance session](https://developer.apple.com/videos/play/wwdc2026/388/) and the installed macOS 27 `StateReporting/SRStateReporter.h` SDK header. Local test: `python3 test/test_p5m_metal_diagnostics.py`.

## Current presentation policy and deadline experiment

The default is immediate submission through the present queue on fixed-rate screens with VSync enabled. VRR screens use CAMetalDisplayLink with preferred frame latency 1, without the additional bounded wait. VSync off keeps immediate presentation unless the user explicitly enables the older tearing experiment. Menu rendering keeps the immediate queue on fixed-rate screens.

The deadline experiment is disabled by default. A visible native-fullscreen HDR session on the fixed 60 Hz test panel received approximately 60 fps but presented only 47.1 fps; the prior queue path presented about 59.5 fps. Average decoded-frame-to-screen delay was approximately 37 ms, with no consistent benefit. These observations justify restoring the previous policy; they do not isolate whether callback scheduling, waiting or compositor behavior caused every skipped source frame.

For explicit experiments, `CHIAKI_METAL_DEADLINE=1` enables the bounded wait and selects the link for VSync video on fixed screens. It selects the newest available frame after reserving the recent p95 of CPU encoding, shared queue delay and GPU completion, plus a 1.5 ms margin. Waiting is capped at half one refresh and skipped near the render deadline. No additional decoded-frame FIFO or intermediate GPU copy is introduced. `CHIAKI_METAL_DEADLINE=0` leaves the default policy; `CHIAKI_METAL_DISPLAYLINK=0` forces the queue and `=1` forces the link.

`[deadline]` logs the wait count/mean and command buffers whose GPU completion exceeded the link's render target. This is a scheduling diagnostic, not a measured count of missed physical refreshes. Compare `[presentation]` and the OS trace before concluding that latency or smoothness improved.

Native fullscreen leaves window size and position to AppKit. The opt-in borderless mode still fills the camera strip. `[presentation-state]` and StateReporting track nonpersonal rendering state and opacity/coverage prerequisites, explicitly without claiming a confirmed direct-to-display path. Use Metal HUD or Instruments to verify the actual compositor path.
